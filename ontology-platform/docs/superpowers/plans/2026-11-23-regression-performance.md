# Python 回归补跑与四阶段性能验收计划

> For agentic workers: use subagent-driven-development; tasks below have separate implementation and verification boundaries.

**Goal:** 补齐当前 Python 回归中可执行的测试，逐项说明剩余阻断，并取得真实 SQL/RDF 服务上的导入、查询、发布、导出时延。

**Architecture:** 沿用现有隔离 Git 工作树；修正测试夹具中已与正式服务冲突的硬编码目标。真实数据库用全新目录和端口的独立实例，性能脚本调用真实本体管线，仅在脚本进程内包装计时，保留正式服务及发布版本。

**Tech Stack:** 当前 Python 3.12、PostgreSQL 17/PostGIS、Java 21/Fuseki 6.2、pytest、现有 local_server HTTP/worker。

**Spec:** 用户于 2026-11-23 要求完成未完成的 Python 回归，无法完成要说明原因；测量导入/查询/发布/导出时延。本计划将该要求落实为以下验收口径。

## 约束与验收口径

- 不把默认跳过改成通过；报告实际运行、失败、跳过数量及原因，并区分轻量服务与旧完整平台测试范围。
- 不启用任何指向正式 PG25459/Fuseki23059 或原迁移源25449/23049 的破坏性夹具。
- 独立测试目录、新凭据、新端口；多个 DSN 必须指向同一已确认测试 PG 实例；恢复测试使用另一独立实例。
- 性能数据为合成 CSV/ZIP，真实 PostgreSQL/Fuseki，不冒称五张图或 CAD 全量导入性能。
- 数据规模、重复次数、字节/条数、是否固定发布版本、失败次数都随结果保存。首遍不等同清空 OS 缓存的冷启动。
- HTTP 202 登记延迟与完整导入完成分别计时；发布包含导航/校验/登记/激活，原子激活另列。查询与导出经 HTTP，导出测完整分页。
- 性能测量避免与本轮实库回归同时执行；已有正式服务后台负载记录为环境条件。
- 密码、连接串、私有备份、活动数据库和原始运行日志不上传；公开报告与脱敏数值证据、脚本、测试同步 GitHub。

## 重点复核

1. 用户误把正式连接串传给测试时，在任何 DROP/CREATE/写入之前拒绝。
2. SQL admin/API/worker 目标混用或恢复源目标相同不能进入实库动作。
3. 计时失败、分页失败和发布失败必须计入失败结果，不只统计成功样本。
4. 小样本 p95 标明样本数，不能据此宣称容量上限；单次首遍与 warm 样本分开。
5. 连接/域名流程完善与测试工作分别交付；没有真实域名/对端/授权时，不声称公网或 SSH 端到端已验证。
