# 部署、私有配置与换机

日常操作先读 [使用指南](使用指南.md)。这是给管理员的新环境准备说明。原生 Windows、Docker、Linux、第二台物理机的执行证据必须分别记录；提供配置文件不代表实际部署已通过。

## 版本与目录

使用 Python 3.12（当前验收解释器 3.12.7）、PostgreSQL 17.11/PostGIS 3.6.2、带 source-file compiler 的 Java 21 JDK/JBR、Fuseki 6.2.0。原生 runner 需要 `jdk.compiler`，普通不带编译器的 JRE 不足；容器走独立 jar 启动。轻量部署只需要 PostgreSQL/PostGIS、Fuseki、HTTP 与串行 worker，不启旧平台 Keycloak、MySQL、S3 或完整应用栈。容器 pin 见 `infra/local-server/versions.lock.json`，沿用既有版本与摘要，没有改用较旧 PostGIS。

建议：

```text
ontology-platform/
  .venv-local-server/              本机新建的 Python 环境（不复制其它项目环境）
  .tools/local-server/             匹配版本的 PostgreSQL、Java、Fuseki
  .runtime/local-server/
    config.json / private.env     私有配置与环境变量
    deployment.json              此部署的全新身份与根目录/端口
    postgres/data/               原生受管 PG 数据
    fuseki/config.ttl             指向本目录内部 TDB2 的配置
    fuseki/databases/            TDB2 数据
    uploads/ imports/ releases/   私有原件、处理中间结果、发布导航
    runtime/                     本部署进程归属、轮转日志
```

`Config.root`、`data_dir` 相对配置文件目录；mapping/review 相对 `root`。`runtime.pg_bin/java_home/fuseki_home` 使用本机工具路径。路径和端口写入私有 JSON，凭据只通过 `*_dsn_env` 与 `auth.write_token_env` 引用环境变量。允许目标列表必须与实际新目标一致。

本版仅实现 IPv4 bind；即使显式允许远程监听，`::1`、`::` 等 IPv6 地址仍会被配置检查拒绝。原生默认使用 127.0.0.1，容器内部使用 0.0.0.0 并只映射主机 IPv4 回环。

## 准备全新的原生环境

1. 在新目录下载/安装上述固定版本，核对项目版本清单中的分发包摘要。不要覆盖旧数据目录。PostGIS 的扩展文件和本机运行依赖必须与 PostgreSQL 17 配套；仅复制 `postgres.exe` 不够。
2. 执行 `powershell -NoProfile -ExecutionPolicy Bypass -File infra/local-server/setup.ps1`（仅本进程执行本项目脚本）；若 Python 不在 PATH，用 `-Python C:\Path\python.exe`。Linux 使用 `sh infra/local-server/setup.sh`。脚本只创建本项目 `.venv-local-server` 并按锁文件安装 Python 依赖。
3. 从项目根运行下面的初始化入口。它只接受全新或完全空的 DATA，校验工具与空闲端口，生成全新部署 UUID、随机账户密码/token、私有 config/env，调用 initdb 并创建四个空数据库及独立管理员/API/worker 角色；完成后 PG/Fuseki 保持停止，不创建应用 schema，不导入数据。无需手工抄写旧身份或密码。
4. **直接新建空服务**：运行 `local-server.cmd init`，再 `start`。**准备恢复备份**：先执行下文 restore 和资产对齐，避免 init 在要求为空的目标创建控制表；核对恢复 ACL/专用权限后再启动。初始审阅快照仍需全量迁移证明后单独 bootstrap，启动不自动导入。
5. 初始化成功标记为 `provisioned-stopped`，私有配置位于所选 DATA 的 `config.json`。若 DATA 改了位置，CMD/Linux 入口设置 `LZO_LOCAL_CONFIG` 指向此文件，PowerShell 使用 `-Config`。失败留下 `provision-state.json` 供检查，不会破坏性地清空并重试；重新初始化应选择另一个全新空目录。
6. 运行 `start`、`status`、`/ready`，实际导入小批次、查询、导出、停止和重启，核对任务与 active release。受管服务会核对清单、可执行文件、工作目录、进程创建时间和命令参数，不接管外来进程。

```powershell
.\.venv-local-server\Scripts\python.exe scripts\provision_local_server.py `
  --root . --data-dir .runtime\local-server `
  --pg-bin .tools\local-server\postgresql-17.11\bin `
  --java-home .tools\local-server\java-21 `
  --fuseki-home .tools\local-server\fuseki-6.2.0 `
  --pg-port 25479 --fuseki-port 23079 --http-port 8792
```

端口均可配置；上例首次恢复选用 25479/23079，是为了与当前备份源的 25459/23059 身份组合区分。恢复按 SQL 的地址/端口/库名及 RDF 的地址/端口/dataset 路径保护来源，跨机器同样写 127.0.0.1 与相同端口组合仍会拒绝，不能据此声称已是新目标。先看备份 manifest 的 source，再选择另一组合；HTTP 仍可使用 8792。DATA 默认限制在 ROOT/.runtime 下，独立新数据盘需额外显式使用 `--allow-external-data-dir`。任何位置都不得复用旧 deployment ID、PID、认证缓存或 private.env。

本机原始迁移来源端口 25449/23049 被原生受管逻辑明确拒绝。模板默认 25459/23059，上述恢复示例明确覆盖为 25479/23079；换端口时同步调整 JSON、允许列表与部署清单。原生 `stop` 不会结束不属于本部署的进程。Fuseki 通过私有 stop-file 通道调用 Jetty/TDB2 的正常关闭 API，超时保留进程与错误，不伪装为已安全停止。

若数据库由系统服务或 Compose 管理，把两个 `managed_*` 设为 false；状态显示 `external`，本命令只管理 HTTP/worker，数据库生命周期由对应服务管理器负责。

## 私有备份选项

选项文件路径值相对选项文件目录。实际数据库列表必须覆盖交付环境中的**所有必要库**，而非照抄下面的示意名字。归档自动枚举每个库全部非系统 schema，包括旧的审阅/CSV schema、新批次、控制元数据、序列、函数、触发器、视图、ACL、角色及扩展清单。

```json
{
  "database_env": {
    "lzo": "LZO_LOCAL_LZO_DATABASE_URL",
    "lzo_gis": "LZO_LOCAL_LZO_GIS_DATABASE_URL",
    "lzo_timeseries": "LZO_LOCAL_LZO_TIMESERIES_DATABASE_URL",
    "lzo_catalog": "LZO_LOCAL_LZO_CATALOG_DATABASE_URL"
  },
  "source_dataset": "http://127.0.0.1:23079/fish_l1",
  "pg_bin": "../../.tools/local-server/postgresql-17.11/bin",
  "assets": {
    "uploads": "uploads",
    "imports": "imports",
    "releases": "releases",
    "cad-imports": "cad-imports",
    "mapping": "../../config/local-server-mapping.json",
    "review": "../../docs/fish/ontology-review"
  },
  "minimum_free_bytes": 1073741824
}
```

只包含确实存在并需要保存的资产目录；初始空目录由 init 建好。导入 CAD/GIS 后必须包含 `cad-imports`：其中保留输入 bundle、原始文件与 SQL/RDF 回读证明，发布版本通过 `cad_source_path` 引用它。尚未导入、目录不存在时可省略这一项。完整 RDF 备份覆盖默认图与全部命名图，采用压缩流与磁盘分块校验，不把整个 RDF 装进内存。SQL 使用 pg_dump 自定义压缩逻辑归档。原文件/导航/OWL/SHACL 按文件大小与 SHA256 核验。不能把活动数据库目录、私有 env、密钥、凭据或进程归属文件纳入 assets。

备份完整性校验不等于真实性签名；应把清单摘要与备份保存在受控位置。完整一致性要求服务与其它源写入者停止，不能只依赖某个瞬间的网页状态。

上例连接变量由 provision 生成，source_dataset 端口应与当前私有配置一致。原生工具路径相对选项文件目录；从其它端口/配置建立的服务器备份时同步调整，不把示例值当作固定目标。

## 新目标恢复

1. 保留原机器和来源数据，不覆盖。新机器按上文准备工具、全新凭据、全新部署身份、空数据库/空 RDF dataset。
2. 配置新私有 JSON 与 env，使其显式允许**新**目标；恢复选项的 `database_env` 标签须与备份 manifest 的数据库标签完全相同；每个值引用新连接的环境变量名。
3. 恢复选项包括 `target_dataset`、`pg_bin`、新的空 `asset_destination`，及经核对后启用 `provision_roles=true`（只建立必要的无登录安全身份，不复制源密码/超级权限）。`asset_destination` 是 staging，如私有选项同目录的 `restored-assets`；不能设为已包含 deployment/PG/TDB 的 `data_dir`。使用 provision 新建的同名专用 API/worker 登录角色时，可显式启用 `reuse_deployment_roles=true`：只复用 Config 声明的非特权同名角色，严格核对 source/target 角色权限和继承属性，保留新密码；其它 LOGIN/高权限冲突仍拒绝。
4. 执行 `restore`，读取 `restored_verified` 结果和 staging 内的 `restore-report.json`。目标不是空、SQL/RDF 指回来源、扩展/对象/行/三元组/文件摘要不符时停止。SQL/RDF 完整回读与资产 staging 恢复完成后，才可继续对齐业务路径。
5. 在同一私有选项中声明完整 `asset_placement`（见下例），执行 `place-restored-assets <备份manifest> --options <选项>`。它先核对清单摘要、完整 SQL/RDF 恢复报告及逐文件 raw SHA256，再检查全部目标和空间；仅将声明的已校验资产复制到空目标，staging 保留。`uploads/imports/releases/cad-imports` 各目录必须落在新 `Config.data_dir` 下的同名目录，因控制表及发布版本的相对引用不能改名。其它 mapping/review/原始资产明确声明位置，不复制 private.env、PID、旧 deployment 或 PG/TDB；不会改变 Native 归属或 data_dir。
6. 对齐必须返回 `assets_placed_verified`，私有报告位于运行目录的 `asset-placement-report.json`。符号链接/路径越界、非空目标、缺少映射或摘要变化会拒绝复制；失败时保留 staging、pending 标记和已产生的失败现场。普通启动及前台 serve/worker 均被阻止，不会自动发布。若同名业务目标已有数据，应核对并使用全新部署恢复，不强行覆盖。不同卷上的显式目标可用，复制与校验采用分块方式。
7. 按对齐声明调整新配置中的 mapping/review 指向；保持原 data_dir 和新部署身份不变。不要对业务 IRI 或 provenance 内容做全局路径替换。逐库核对角色、扩展、schema、完整表/关系，并验证每条任务 source_path、release 导航引用能在新根解算。新账号需要补权限时，由管理员只授专用 API/worker 权限。
8. 最后运行 `start`，实际查询/导出、停止和重启。确认新目录 PID/创建时间/可执行文件和部署身份。Windows 同机新路径、Linux/跨 OS、第二台物理机分别记录，不能互相替代。

下面的标签与上文 assets 示例对应；实际必须按 `manifest.assets` 中真正出现的 label 集填写，不能漏标签或照抄不存在的标签。空目录不形成资产文件记录，其 label 若未出现就省略；未来导入会按需创建业务目录。原始资料若另有 `original` 等标签，也要显式映射到新的私有位置。所有路径可配置，不要求特定盘符：

```json
{
  "asset_destination": "restored-assets",
  "asset_placement": {
    "uploads": {"base": "data", "path": "uploads"},
    "imports": {"base": "data", "path": "imports"},
    "releases": {"base": "data", "path": "releases"},
    "cad-imports": {"base": "data", "path": "cad-imports"},
    "mapping": {"base": "data", "path": "restored-mapping"},
    "review": {"base": "data", "path": "restored-review"}
  }
}
```

`base` 仅允许当前配置的 `data`、`root` 或 `review` 根，`path` 为该根下的安全相对目录。mapping/review 的文件名保留，例如 mapping 文件还原至 `data_dir/restored-mapping/local-server-mapping.json`。源备份和目标 staging/业务路径分别配置；完整示例路径可用 `backups/backup-2026-11-12/manifest.json`，这些私有备份/原件不得进入公共仓库。

`Config.mapping_file` 必须位于 `Config.root` 内。上面的 `base=data` mapping 示例仅适用于 DATA 也在 ROOT 内的默认部署；若 DATA 是 ROOT 之外的独立数据盘，应把 mapping 明确放回 ROOT 下的单独空目录，例如 `{"base":"root","path":"config/restored-mapping"}`，随后将 `mapping_file` 配为 `config/restored-mapping/local-server-mapping.json`（以备份实际文件名为准）。核对还原文件 SHA256 与清单 `raw_sha256` 一致，不能把配置指向 ROOT 外的 DATA/mapping 文件来绕过限制。其它业务原件仍可保存在外置 DATA。

默认要求新空 SQL/RDF 目标。若一次完整恢复被中断，可在核对失败报告后显式设置 `resume_verified_targets=true`：已恢复目标只有与备份完整 inventory/摘要一致才会跳过，部分、不符或被改动的目标仍拒绝；它不会清空、合并或覆盖现有目标。staging 仍须按恢复模块要求准备，不能以“续传”绕过路径/资产校验。

新旧管理员名称不同时，恢复模块会按源清单核对扩展名称、版本、schema 和成员身份，局部恢复目标扩展成员的对象归属，随后完整核对 owner、ACL、定义和行值。PostGIS 3.6.2 的跨管理员独立实库用例已经验证；它保留新机密码及安全源身份，不执行跨库的全局归属重分配。第二台物理机器与跨系统尚未实际执行，详见[验收记录](server-readback.json)。

## 初始审阅快照登记

管理员先完成现有 SQL schema、五个发布 RDF 图与导航文件的实际验证，生成私有 proof JSON：`status="passed"`、`sql_verified=true`、`rdf_verified=true`、`raw_payload_public=false`、完整 `sql_schemas` 和与导航 manifest 一致的 `rdf_graphs`。

```powershell
.\infra\local-server\local-server.cmd bootstrap-release --proof .runtime\local-server\bootstrap-proof.json
```

该命令在当前配置的新 SQL/Fuseki 目标检查 schema/图存在性，复制私有导航快照并校验文件后，登记初始只读 release。proof 是管理员已完成全量迁移验证的证明；图存在性检查本身不替代全量验证。已有 active release 时必须显式使用 `--replace-active` 才能切换。服务启动与重启不会自动执行 bootstrap。

## 轻量 Compose（本机未执行）

本交付无 Docker 引擎，镜像构建、容器运行与容器内恢复尚未验收；版本 pin 和配置不能当成已通过的无损恢复证明。它们也不表示已开启本机虚拟化或安装 Docker。

准备私有 `.runtime/local-server/compose.env`，按 `infra/local-server/compose.env.example` 填入四个不同随机值，数据库密码使用 URL 安全字符。然后从项目根目录运行：

```sh
docker compose --env-file .runtime/local-server/compose.env -f infra/local-server/compose.yml up -d postgres fuseki
docker compose --env-file .runtime/local-server/compose.env -f infra/local-server/compose.yml run --rm api init
docker compose --env-file .runtime/local-server/compose.env -f infra/local-server/compose.yml up -d api worker
```

HTTP 仅映射到主机 127.0.0.1:8792，数据库端口不映射到主机。四个服务使用独立持久卷和日志轮转；只在容器运行模式下使用 Compose restart 策略。停止使用 `docker compose ... stop`，不要用 `down -v` 删除数据卷。完整恢复前实际核对容器 PostgreSQL/PostGIS 版本和扩展匹配；新机/跨 OS 的最终验收仍需执行。

本 profile 两个 Dockerfile 各自的 `.dockerignore` 默认拒绝全部文件，仅白名单发送公开 local_server 源码、顶层 Python 脚本、映射与已发布浏览成果、此轻量 profile 所需配置，并在末尾再次排除 env、活动库、工具、venv、备份、密钥、token、PID 与私有配置。根 `.dockerignore` 保留既有规则，只追加本地运行目录排除，继续支持原 backend/database 构建上下文。不要删除这些边界来处理本机运行资产。
