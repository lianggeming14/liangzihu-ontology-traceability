## 数据库和进程权限

PostgreSQL 的只读检查确认：admin 为超级用户，API/worker 使用非超级用户角色；回环认证采用 SCRAM。业务 API 的可读表和任务/发布操作权限有区分。这里验证的是当前服务角色，不是对所有系统账户和权限的完整认证。

Fuseki 在回环地址上可无凭据执行查询；本轮没有为验证权限而发送 SPARQL Update。回环监听限制网络入口，但不提供本机每用户授权。当前 HTTP 进程环境也包含 admin DSN，说明 API/worker/管理进程之间的秘密隔离仍可改善；没有把“数据库角色不同”误报为“各进程只持有自己的秘密”。

正式私有配置 ACL 未发现 Everyone、Authenticated Users、Builtin Users 的直接授权；存在继承的运行环境组/SID 权限，尚未逐一确认其归属。不能删除未知 SID 来假装完成最小权限，也不能据此宣称只有一个账户可读。新建测试实例独立使用其生成的私有凭据。

## 补齐后的实施顺序

1. 明确本机是访问端还是被访问端，保留实际命令、端口和报错。先区分 TCP 拒绝/超时、SSH 用户认证、转发拒绝、HTTP 401/403。
2. SSH 方案：管理员核对并安装服务，检查运行账号、`sshd_config`、公钥路径及 ACL，再验证本机 SSH 登录、跨机登录和端口转发。管理员组账号与普通账号的公钥规则分别核对；当前没有服务配置，不能预填验证通过。
3. HTTPS 方案：确认域名归属、DNS/NS/DNSSEC 权限、Cloudflare 目标账户和 zone；准备 IdP/OTP 与精确允许人员，先创建覆盖全站的 Access 应用，再发布路由。
4. 实现并测试应用的正式 Host、精确 HTTPS Origin；连接器使用自己的 Tunnel token，回源 `http://127.0.0.1:8792`。核对 team/AUD 和 JWT 验证，不以仅有请求头作为身份验证。
5. 分别验证 DNS、证书、Tunnel、入口登录、应用读取、授权上传、拒绝身份、服务账号权限及重启恢复。某一层通过不能替代下一层。

域名、Cloudflare 账户/资源权限、实际远端设备和提升后的系统检查仍未提供验收证据；公网或 SSH 端到端状态保持**未验收**。网络出站检查也要区分 TCP/UDP、TLS 和真实 team 域名，不能拿历史 TCP 探测替代完整隧道测试。

本轮认证探测前后正式 active release 一致，未产生业务写入。原始检查日志与配置均留在私有运行目录，公开文档不包含账号口令、token、连接串或 Windows SID 清单。
