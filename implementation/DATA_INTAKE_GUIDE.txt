梁子湖农业知识库：数据接入操作指南 v0.3
更新：2026-10-14
适用：implementation 本地工程版；以当前 API 契约与页面为准。

一、这版聚焦什么

本版负责：接收原文与原件，识别声明的来源/载体/记录类型，按已登记本体执行明确映射、类型与单位校验，保存对象、关系、证据和处理历史，再提供查询结果。
本版不执行图像识别、视频抽帧、OCR、农业诊断、可信度打分、自动因果推断或设备控制。外部处理程序通过接口读取证据并提交候选结果。
既有设备计划、边缘网关、物料事件与消费者溯源功能保留为兼容扩展，不作为本体库的新建主流程。不要为完成数据库接入而同时部署完整采集与业务平台。

启动：运行 implementation/启动系统.cmd，访问 http://127.0.0.1:8787/。
主导航：数据库总览、本体管理、数据接入、对象与关系、原件与断言；兼容扩展折叠为批次与溯源、设备采集。
本体卡片可“查看结构”“编辑名称”；数据接入页可“登记来源映射”“接收结构化记录”，映射条目可“用样本预览”，回执可“选择映射重试”。
本机演示登录只用于合成数据操作；正式接入需配置受控身份。数据库按租户隔离。API 文档：GET /api/v1/openapi.json。
所有 POST 写接口均需 Authorization: Bearer <受控令牌> 与 Idempotency-Key: <唯一请求键>；只读 POST /ingestion/preview 无需幂等键。
本指南中的 UUID 必须换成实际接口返回值；地址、令牌和厂家编号均为占位说明，不代表已接通真实设备。

二、先登记本体，再登记对象

1. 创建本体时填写可读名称、稳定 package_id、版本和命名空间。
2. 定义类：type_id、中文 label、identity_type。身份类型表示实体是什么，语义类表示该实体在本体中的分类；不能仅因名称相同就合并对象。
3. 定义属性：property_id、label、applies_to 类列表、value_type、usage。按需设置 unit、enum_values、required、cardinality、minimum、maximum。
4. 定义关系：明确主体/客体身份类型；如需更严格分类，再声明主体/客体语义类。使用有效时间、限定条件和证据，不把任意两个名称直接连成事实。
5. 创建对象并分配语义类，确认分类有效期覆盖待导入记录的发生时间。

完整示例一：POST /api/v1/ontology/packages
{
  "package_id": "liangzihu.water",
  "version": "1.0.0",
  "namespace": "urn:liangzihu:water:",
  "label": "梁子湖水体监测本体",
  "description": "登记水体对象与观测属性；数值范围为本项目示例配置，需业务人员确认。",
  "types": [
    {"type_id": "pond.water", "identity_type": "pond", "label": "池塘水体"}
  ],
  "properties": [
    {
      "property_id": "water.temperature",
      "label": "水温",
      "applies_to": ["pond.water"],
      "value_type": "decimal",
      "usage": "observation",
      "unit": "Cel",
      "cardinality": "single",
      "minimum": -10,
      "maximum": 80
    },
    {
      "property_id": "water.condition",
      "label": "外部报告的水体情况",
      "applies_to": ["pond.water"],
      "value_type": "enum",
      "usage": "assertion",
      "enum_values": ["normal", "attention"],
      "cardinality": "single"
    }
  ],
  "predicates": []
}

完整示例二：POST /api/v1/ontology/entities
{
  "entity_type": "pond",
  "name": "梁子湖一号塘",
  "attrs": {},
  "semantic_types": [
    {
      "package_id": "liangzihu.water",
      "version": "1.0.0",
      "type_id": "pond.water",
      "valid_from": "2026-01-01T00:00:00+08:00"
    }
  ]
}
保存响应中的 entity_key，后文用 <池塘UUID> 表示它。
旧对象可通过 POST /api/v1/ontology/type-assignments 单独分类；带 entity_key、package_id、version、type_id、valid_from，必要时加 valid_to。分类生效时间不能无依据追溯到历史。

属性类型支持 decimal、integer、boolean、string、enum、datetime。数字不等于文本、false 不等于 0；datetime 需要时区。unit 必须与定义完全一致；未定义单位的属性不要随意填写单位。多值属性使用数组；必填目前只用于 attribute（对象属性），不要求一次上报所有观测。
同一 property_id 若存在多种有效版本，必须提供明确 property_ref；后端也检查对象在该时点是否属于属性适用类。没有唯一对应关系会返回 needs_mapping，不按属性中文名称猜测。

三、修改名称与维护版本

GET /api/v1/ontology/packages 返回可读名称、类/属性/关系列表、display_revision 和不可变定义。
POST /api/v1/ontology/package-labels 可以修改本体名称、说明，以及各类/属性/关系的显示名称。例如：
{
  "package_id": "liangzihu.water",
  "version": "1.0.0",
  "expected_revision": 1,
  "label": "梁子湖池塘与水质知识库",
  "description": "供水质数据映射和查询使用。",
  "type_labels": {"pond.water": "养殖池塘水体"},
  "property_labels": {"water.temperature": "池塘水温"}
}
expected_revision 使用最近 GET 返回的 display_revision。并发修改会返回 display_revision_conflict；先刷新再修改。
显示名修改保留稳定标识和已有引用。本体已发布版本的类边界、属性类型/单位、关系语义不能覆盖；改变含义必须发布新版本并检查对象分类、来源映射和历史查询。当前不提供自动迁移整个历史库或完整草稿审批工作流。

四、接入前明确四个维度

来源：source_id 是来源系统标识；source_category 为 device / manual / external_system / model。
载体：结构化转换目前使用 content_type=application/json。图片、视频、PDF 等文件走原件接口，再引用 evidence_id。
记录类型：record_kind 为 entity / observation / assertion / event / relationship / evidence；未知字符串可接收为待映射回执。
本体对应：固定对象 subject_key、属性 property_ref（package_id/version/property_id），或标准实体/关系载荷中的类和关系引用。

摄像头、图片、天气、人工不是同一级概念。摄像头是设备来源，JPEG 是载体，图片原件是证据；水温是由映射选定的属性。一个 temp 字段不会自动被解释为水温。
天气实测与预报必须使用不同记录契约：实测可为 observation，预报应作为 assertion，origin=forecast，并在值中保留适用时间/范围。数据库不会自动把预报当成实测。
来源分类依据管理员登记的契约和提交声明，不是对发送方身份真实性的证明。本版尚未实现令牌到 source_id 的强制绑定；正式部署需由 API 网关或认证集成完成该约束。

五、登记明确的来源映射

POST /api/v1/ingestion/mappings；仅 admin / ontology_admin 可登记。
必填：mapping_id、version、source_id、schema_version、source_category、content_type、record_kind、target_action、mode。
mode=fields 时至少一条 field_rules；mode=identity 时接收目标接口标准载荷，不能同时带转换规则。
可选：subject_key 固定对象、defaults 固定目标字段、description 管理说明。
source_id/schema_version/source_category/content_type/record_kind 必须与来件完全匹配；mapping_id+version 不可覆盖，修改规则要新建版本。

完整示例三：接收设备以 0.1℃ 为单位的整数读数，显式转换为 Cel。
{
  "mapping_id": "pond-01-water-temperature",
  "version": "1",
  "source_id": "liangzihu-sensor-platform",
  "schema_version": "sensor-json-v1",
  "source_category": "device",
  "content_type": "application/json",
  "record_kind": "observation",
  "target_action": "create_observation",
  "mode": "fields",
  "subject_key": "<池塘UUID>",
  "description": "仅接收一号塘已核对的水温字段；来源单位为 deci-Cel。",
  "defaults": {
    "property_id": "water.temperature",
    "property_ref": {
      "package_id": "liangzihu.water",
      "version": "1.0.0",
      "property_id": "water.temperature"
    },
    "method": "platform sensor import",
    "origin": "measured"
  },
  "field_rules": [
    {
      "source_path": "/readings/temperature",
      "target_path": "/value/value",
      "value_type": "decimal",
      "scale": "0.1",
      "offset": "0",
      "source_unit_path": "/unit",
      "source_unit": "deci-Cel",
      "unit": "Cel"
    },
    {
      "source_path": "/captured_at",
      "target_path": "/observed_at",
      "value_type": "datetime"
    }
  ]
}

field_rules 使用 JSON Pointer，不执行代码。/a~1b 表示键 a/b，~0 表示 ~。支持读取数组下标；写入目标以对象字段为主，复杂参与者数组可整体映射或使用 identity 标准载荷。
value_type 可为 decimal/integer/boolean/string/datetime。decimal 使用十进制 scale 与 offset；本例 225 * 0.1 + 0 = 22.5。source_unit/source_unit_path 必须成对出现；错误来源单位拒绝转换。
enum_map 可明确转换枚举，如 {"0":"closed","1":"open"}；未映射的值进入校验失败，不默认为关闭/正常。枚举转换不与缩放/其他类型转换混用。
unit 只用于 /value/value 的同级 /value/unit。转换规则不能写 evidence_ids、status、origin；证据与候选状态由接入流程控制，来源性质由固定契约与标准载荷声明。
相同或包含关系的目标路径禁止重复写入，字段规则不能靠顺序悄悄覆盖同一值。

六、先预览，再正式接收

完整示例四：POST /api/v1/ingestion/preview 或 POST /api/v1/ingestion/receipts 使用同一信封。
{
  "source_id": "liangzihu-sensor-platform",
  "source_record_id": "pond-01-reading-20261014-080000",
  "schema_version": "sensor-json-v1",
  "source_category": "device",
  "content_type": "application/json",
  "record_kind": "observation",
  "mapping_id": "pond-01-water-temperature",
  "mapping_version": "1",
  "payload": {
    "readings": {"temperature": 225},
    "unit": "deci-Cel",
    "captured_at": "2026-10-14T08:00:00+08:00"
  }
}

预览返回 status、would_store、issues、normalized_payload；read_only=true。status=stored 表示按当前状态可入库，不代表已提交。预览不留下对象、观测、证据、回执、审计、outbox 或幂等记录。预览后数据库可能改变，正式接收仍重新校验。
正式接收返回持久回执 id、raw_evidence_id、raw_envelope、mapping_id/version、status、issues、record 和 attempts。

三种接收状态：
- needs_mapping：未指定映射、映射不存在、类别未支持，或本体类与属性无法唯一对应。
- validation_failed：已找到映射，但字段缺失、类型/单位/范围/时间/引用错误，或来源契约与映射不匹配。
- stored：目标写入与回执处理记录已提交，表示满足写入规则，不表示事实已被证实。

“合法信封”指来源记录标识等必要外层字段完整。缺少 source_record_id、JSON 不合法、未认证、无权限等请求直接报错，不创建回执。合法但未能转换的数据保留原文和错误。
外层 evidence_ids 若包含不属于本租户的证据，直接拒绝；不允许借由接收回执读取他人原件。

source_record_id 必须使用来源系统稳定事件编号。同租户+source_id+source_record_id 同内容重放返回原回执；内容改变返回 source_record_conflict，不覆盖原文。mapping 选择不计入原始业务内容哈希，改变映射通过重试接口执行。
不要用新随机 source_record_id 掩盖冲突。来源数据确实修订时，应使用来源新的修订记录标识，并在原始载荷中保留旧记录关联。

七、查询和重试

GET /api/v1/ingestion/mappings?source_id=liangzihu-sensor-platform&limit=100&offset=0
GET /api/v1/ingestion/receipts?status=needs_mapping&limit=100&offset=0
GET /api/v1/ingestion/receipts/<回执UUID>

先修复本体分类或登记新映射版本，再调用：
POST /api/v1/ingestion/receipts/<回执UUID>/retry
{
  "mapping_id": "pond-01-water-temperature",
  "mapping_version": "2"
}
需要新 Idempotency-Key。旧原文不会重写，attempt_number 逐次增长，每次保留采用的映射版本、标准化结果和错误。单回执最多 100 次处理尝试；超过时应检查来源与设计，不能无限循环重试。
成功 stored 后禁止再次生成业务记录。修订已入库信息要通过新的来源修订记录及既有修订机制处理。
未知来源类别或不支持载体不是改映射版本就能修复：应先补充受支持的来源契约/外部转换适配器；本版不提供篡改原信封类别的入口。
所有列表依据 next_offset/truncated 分页。列表可筛选来源和状态；不要把第一页当成全量。

八、人工录入与文件原件

人工录入仍可使用 POST /api/v1/ingestion/manual，record_kind=observation/assertion/event，payload 为标准记录。原始表单、操作者与接收时间生成证据，并与记录原子提交。人工观测 origin=reported；人工陈述进入候选状态。此便利接口失败时整条事务回滚；需要持久失败队列时使用通用 /ingestion/receipts。
本体字典已经登记时，人工与 API 写入均执行相同后端校验。选择对象后应选择其适用属性，不再自由填写一个未登记属性就作为受校验观测入库。

文件：POST /api/v1/ingestion/assets，multipart 字段 file、source_kind、source_id；仍需幂等键。source_kind 是旧文件接口的兼容分类，例如 image/video/document，不等同于四维信封中的 source_category。
原文件单个最大 32 MiB，结构化 JSON 最大 2 MiB。保留原文件字节、SHA-256、文件名、声明 MIME、检测载体信息与来源；不会计算亮度、感知哈希、农业特征，也不会视频抽帧。
载体检查用于核对声明与文件格式，不是内容识别。未知格式保留原件并明确状态；被声明为图片但格式不匹配时不得显示为已识别图片。
响应 metadata 区分：
- integrity：接收时内容哈希检查；
- carrier：载体识别与格式状态；
- processing.status=not_requested、scope=external_service：未调用外部处理。
外部未处理不影响完整原件的受保护查询与下载。GET /api/v1/evidence/<证据UUID>/asset 返回原件；读取时检查当前文件哈希。文件缺失、损坏、撤回或仅外部引用与“尚未识别”分别处理。

九、外部模型或报告结果怎样回来

本体库不调用模型。外部程序先读取受保护证据；运行后以 source_category=model、record_kind=assertion 回传，映射也必须明确绑定该类别。信封必须有 producer={"name":"外部模型名称","version":"明确版本"}，并在 evidence_ids 中引用输入原件。
可登记 mode=identity 的映射，target_action=create_assertion，payload 按标准断言格式提交 subject_key、predicate_id、property_ref、value 等。结果强制 origin=model、status=candidate；记录值不由本库重新推断。
断言属性须 usage=assertion。未明确对应属性的历史/兼容断言可标 unvalidated；不能把它直接采纳为已验证事实。模型版本、原始结果、采用映射版本与原件链接均可从回执追查。
人工认可或外部业务采纳是独立流程；结构校验通过与原件哈希正确均不等于农业结论正确。

十、输出与旧功能兼容

对象：GET /api/v1/ontology/entities；属性：GET /api/v1/ontology/properties；观测与断言：GET /api/v1/observations、/assertions。
关系与关系网：GET /api/v1/ontology/relations、/ontology/graph；对象集：GET/POST /api/v1/ontology/object-sets。
证据包：GET /api/v1/inference/bundles/<对象UUID>；变更游标：GET /api/v1/trace/changes。
JSON-LD/Turtle 导出沿用 /api/v1/ontology/export。导出是受限查询结果投影，不声称具备任意 OWL/RDF 无损往返能力。

输出区分 validation_status、原件完整性/载体状态/外部处理状态、候选/采纳状态。接收回执保存当时处理结果；若要判断当前证据可用性，应重新查询证据包，不依赖旧幂等回执。
旧属性自由字段与历史记录不被删除或自动标成已校验。旧本体显示 legacy_unvalidated，可逐步登记属性字典并建立新版映射。修改名称不改历史语义，升级定义不自动重写旧数据。

兼容扩展仍保留：devices/device-policies/device-records、ops/edge_gateway.py、物料与溯源接口。网关采集/RTSP 取帧属于外部采集层，可单独运行；不是本体库核心的图像处理能力。新核心通用接入只接巡检、灌溉、维护、异常这类现场事件，不推动库存出入库。现有业务系统应作为其权威记录来源。

十一、验收与现实限制

建议先用一类对象、一个属性、一份真实但脱敏的来源样本完成：登记定义→对象分类→登记映射→预览→正式接收→重复重放→错误单位→修复后重试→查原件与证据包。
再分别验证模型候选、手工观测和图片原件，确认三者未被混淆。
当前不包含：厂家设备实连、统一身份来源绑定、自动同义合并、通用可信度判断、自动历史迁移、任意模型执行、大规模流式处理。PostgreSQL 实库、生产权限/TLS、并发容量、备份恢复、厂商字段含义仍需现场验收。
合成 SQLite/HTTP 测试只能证明所覆盖的本地行为；测试结果与跳过项以本次交付验证报告为准，不能作为生产或田间验收结论。
