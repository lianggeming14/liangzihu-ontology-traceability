梁子湖农业本体知识库 v0.3：数据库核心范围与实现说明
更新：2026-10-14
定位：可扩展、可校验、可追溯的农业知识底座及必要管理界面。

一、范围收敛

核心链路：来源声明与原文接收 → 显式分类/映射 → 本体约束校验 → 对象/关系/记录与来源持久化 → 受控查询和数据交付。
数据库处理“资料是什么、对应什么、是否满足结构约束、如何追溯”，不代替农业专家或模型判断内容真假。

保留在核心：
1. 类、属性字典、关系语义、对象身份和语义分类；
2. 本体显示名维护、不可变语义版本、对象集；
3. 来源契约、字段映射、时间/单位/枚举的确定性转换；
4. 原文/原件证据、处理回执、错误队列、重复提交和修订历史；
5. 观测、事件、候选断言及其来源关联；
6. API、关系查询、原件查询、证据包、变更游标。

从核心退出：摄像头持续拉流、视频抽帧、图像特征与农业识别、OCR、可信度打分、自动因果判断、设备控制、完整库存与发货流程、消费者溯源界面。
既有外围代码没有无依据删除，而是作为兼容扩展保留。它们不构成 v0.3 核心完成的必要条件，不在此版继续扩展。
数据库不得同时维护一份与梁子湖原业务平台竞争的权威库存；接轨时以原平台业务记录与来源编号为依据。

二、五大重点在库中的具体含义

1. 概念与身份
- 稳定实体 entity_key 用于关联，不以中文名称当主键。
- identity_type 表示身份类型；语义类 type_id 按本体 package_id + version 登记。
- 属性必须声明 applies_to，定义概念适用边界；同名属性不代表同义，语义一致须由管理员明确映射。
- 对象分类有有效起止时间，历史观测对应的是观测发生时有效的语义类。
- 显示名称可改；标识、单位、类型或适用类的含义变化用新的本体版本，不覆盖旧版本。
- 当前不进行自动实体去重/同义合并。来源对象与内部对象通过已知 UUID、固定 subject_key 或明确映射关联。

2. 关系语义
- Link Type 对应已登记谓词，具有主体/客体身份类型；可进一步限定语义类。
- 具体关系记录主体、谓词、客体、有效时间、限定条件和证据。
- 通过核心接入映射新建的关系为 candidate，不因技术校验通过自动接受。
- 空间、生产、事件、观测、断言、证据等关系可按维度查询；图是关系数据的视图，不能用画一条线替代语义与证据定义。
- 稳定标识链接不同领域对象；不要求所有农业本体都归入水稻或小龙虾专有类型。

3. 时空与事件
- observed_at/occurred_at 为声明的业务发生时刻，必须有时区；created_at/recorded_at 表示系统接收或创建时间。
- 观测发生时间用于类适用性校验；空间上下文作为明确数据保存，不从图片推测地点。
- 事件独立于静态属性。核心通用接入支持巡检、灌溉、维护、异常现场事件，不引起库存修改。
- 采集计划时间与实际采集时间不能互相替代，旧设备扩展继续保留这一区分。
- 当前不是完整双时态数据库；并未实现任意 known_at 历史重建。历史回执、语义版本和变更记录不能冒充全库任意时点快照。

4. 观测与证据
- Observation 表示按明确属性、对象、方法和时刻提交的读数，区分 measured/reported/estimated。
- Assertion 表示一个来源作出的说法；模型结果强制 origin=model，初始 candidate。未来天气预报作为 forecast 断言，不混入实测。
- 原文件保存字节哈希，人工和结构化接入保留规范 JSON 回执及操作者、租户、接收时间。
- SHA-256 证明本库留存字节或规范 JSON 的完整性，不证明输入真实、来源已认证或结论正确。
- Evidence 可同时支持多个记录，记录始终能追查到来源、映射版本和原文。

5. 约束与推理接口
- 后端统一校验属性适用类、有效时间、类型、单位、枚举、数量、必填、数值边界和引用对象。
- 明确不匹配的数据进入校验失败；无法唯一解释的数据进入待映射。不以空字符串/0/猜测值补齐缺失。
- 校验、原件完整性、载体格式、外部处理状态、候选/采纳状态是不同维度。
- 推理层接收明确事实来源、候选说法、缺口与证据；本库不实现通用因果推断或自动农业决策。
- 数据血缘只能证明“结果经过哪些处理依赖哪些输入”；因果链需要外部模型或专家提出带证据的候选解释。记录来源不能直接被说成已证明原因。

三、主要概念与工程落点

Object Type / Class：领域包中的语义类定义；identity_type 指向通用或已登记扩展身份类型。
Object：entities 中具有稳定 entity_key 的对象；type_assignments 表达语义分类及有效期。
Property：ontology_properties 中按包版本登记的属性，区分 attribute/observation/assertion 用途。
Primary Key：数据库唯一性与关联机制；来源记录编号用于来源内去重，不替代对象身份模型。
Link Type：ontology_predicates 中的关系语义；relations 保存具体关联、时间和证据。
Action Type：受权限控制的数据库服务操作目录。它不代表已接通闸门控制或任意外部执行服务。
Object Set：按条件动态筛选或固定成员快照；现有基础过滤和跨页成员选择继续可用，不增加任意查询执行语言。
Lineage：原件→回执→映射版本→处理尝试→标准记录→关系/查询输出。每次重试追加历史，既有原文不可覆盖。

四、分层结构

外部来源层：梁子湖原平台、传感器平台、人工、官方 API、外部模型。
外部适配层：完成厂家认证、网络访问和专有协议解析，向本库推送标准 JSON 或原件；不放入数据库事务。
核心接入层：合法信封检查、四维分类、不可变映射、规范转换、失败队列与幂等。
本体约束层：OntologyService 校验类属性、单位、类型、引用、时间、关系端点。
存储层：事务数据库保存结构和回执，受控资产目录保存原文件；二者通过 SHA-256 和证据标识关联。
查询层：对象、关系、记录、对象集、证据包、回执与变更游标。
应用层：管理界面用于维护和校验；溯源展示、模型推理、业务流程作为数据使用方。

运行时组合为 IntakeService → OntologyService → FieldService → DeviceService → Service。
这是一条为保持已有行为兼容而采用的服务继承链，不表示设备与业务扩展在逻辑上属于核心数据库边界。

五、v0.3 新增数据结构与一致性

003 迁移：ontology_properties、ontology_display、semantic_validations，分别保存属性字典、可读名称覆盖与校验状态。
004 迁移：intake_mappings、intake_receipts、intake_attempts。

intake_mappings：主键为 tenant_id/mapping_id/version；definition 和 content_hash 固化映射。source_id/schema_version/record_kind 列辅助查询；来源类别和 content_type 在 definition 内完整保存并验证。
intake_receipts：同租户 source_id/source_record_id 唯一；保存原始信封、内容摘要、原文证据、最新状态和目标记录。
intake_attempts：按 receipt_id/attempt_number 追加每次处理，保留映射引用、标准载荷、错误、目标与当次结果。

业务目标写入采用 SAVEPOINT。字段校验或目标创建中途失败回滚目标业务写入，但保留外层合法接入原文和失败尝试；不得留下半个对象或半个事件。
正式接收与重试均沿用父服务的租户事务锁、幂等、审计和 outbox。预览用独立事务保存点试写并完整回滚，不发布事件，不保存临时证据或生成的目标 UUID。
同一来源记录内容完全相同的并发重放仅产生一份目标记录。内容变更返回 409，旧原文不被覆盖。
已 stored 的回执禁止再次写业务数据。每条最多 100 次处理尝试，避免无限失败重试。

SQLite 是本地持久开发后端，PostgreSQL 是单独验收的部署后端。两类迁移文件分别保存，启动按版本与校验和升级，001/002 既有迁移不原地改写。

六、本体属性校验的实际边界

property_ref 明确引用 package_id/version/property_id。若观测不带 ref，只允许从对象在 observed_at 时有效的分类中解析唯一适用属性；零个或多个候选均待映射。
属性 usage：attribute 用于对象自身属性；observation 用于观测值；assertion 用于候选说法的受控取值。不能把用途错误的属性复用为另一类记录。
值类型：decimal、integer、boolean、string、enum、datetime。数组需 cardinality=many。required 只用于对象 attribute，不要求一次上传所有观测。
单位完全匹配；单位转换在来源映射显式声明，不在属性校验器内偷偷转换。
数值上下限是管理员登记的数据约束，不是系统自行生成的农业安全阈值。
关系按声明的身份类型及可选语义类校验。继承推理、OWL 等价类、跨库同义推导与任意逻辑规则引擎未在此版实现。

显示名更新通过 ontology/package-labels，expected_revision 防止覆盖他人修改。稳定 ID 与版本引用保持不变。定义改变需要新版本；当前没有通用草稿/发布审批、自动迁移、删除已引用定义的完整编辑器。
旧记录保留并标 legacy_unvalidated 或 unvalidated，不伪造已经完成字典校验。旧系统并非全部自由字段自动转成正式属性。

七、来源与映射契约

信封必填 source_id、source_record_id、schema_version、source_category、content_type、record_kind、payload。
选择映射时 mapping_id/mapping_version 成对出现；可带 evidence_ids；模型另带 producer.name/version。
支持来源分类 device/manual/external_system/model。JSON 原文解析仅支持 application/json；其他载体使用文件原件接口或外部适配器，不能任意猜字段含义。

映射必填 mapping_id、version、source_id、schema_version、source_category、content_type、record_kind、target_action、mode。
- identity：采用目标接口的标准 payload，经同一后端语义校验。
- fields：通过 JSON Pointer 读取字段，显式写入目标属性；支持精确十进制 scale/offset、源单位匹配、枚举表和含时区时间。
- subject_key：把一个具体来源映射绑定到固定已有对象，防止未经定义改变监测对象。
- defaults：明确目标 property_ref、方法等固定信息。
不使用 eval、任意脚本、自动 temp 语义猜测或后台 worker。

枚举未知或单位错误进入 validation_failed。没有映射或未支持类别进入 needs_mapping。原有未知类别要通过受支持的新来源契约/外部适配器处理，本版没有编辑原始信封后伪装成功的功能。
原始内容摘要排除 mapping 选择字段，保证映射修正不被误判为来源原文改变；初次提交完整信封仍保存在 raw_envelope 与原文证据中，后续采用版本记录在每次 attempt。
字段规则最多 100 条、JSON Pointer 最深 8 层，结构化请求最大 2 MiB。十进制转换有有限数字和精度预算；这不是无限精度计算服务。

八、文件完整性、载体与外部处理分开

asset_inspection 执行必要的格式/载体检查，原件内容由 asset://SHA256 引用；文件名和请求 MIME 不作为唯一格式证据。
新文件接入不再执行 agri/media.py 的图像指标或视频抽帧；旧文件与既有派生记录保留历史，但不能说它们是 v0.3 新接入必须完成的步骤。
上传metadata包含 integrity、carrier、processing 三类信息。processing 默认 not_requested / external_service。
证据包 checks 区分 integrity_status、carrier_status、external_processing_status 和 truth_assessment=not_performed。
原件完整且可读取与“外部算法已经处理”彼此独立。未配置 FFmpeg、未识别图片不会被当成原件损坏。
不匹配/损坏载体需明确标记；available/usable_for_inference 这类兼容字段只能解释为技术材料可用性，不是农业事实可靠度。
内嵌 JSON 证据通过 canonical_json 与 receipt 内容同时验证。它保留 JSON 语义结构而不承诺保留 HTTP 请求的空白、字段顺序或字节编码。

外部文件引用只有 reference_only 时不能宣称本地已检验原件。大文件哈希检查有 I/O 成本；当前实现不宣称已有生产级对象存储、缓存、异步校验或恢复编排。

九、输出给代码层与溯源系统

代码层通过标准查询取得有稳定标识的数据，不依赖屏幕截图或本体卡片 JSON 的排版。
推荐接口：
GET /api/v1/ontology/packages、/ontology/properties：发现定义、显示名称与版本。
GET /api/v1/ontology/entities、/ontology/relations、/ontology/object-sets：对象与关系。
GET /api/v1/observations、/assertions、/trace/events：按语义类型读取记录。
GET /api/v1/ingestion/mappings、/ingestion/receipts、/ingestion/receipts/<id>：映射与处理血缘。
GET /api/v1/evidence/<id>、/evidence/<id>/asset：证据元数据与受保护原件。
GET /api/v1/inference/bundles/<entity_key>：聚合资料，包含证据、候选/已采纳断言、缺口及检索范围。
GET /api/v1/trace/changes：以租户绑定游标读取提交顺序事件。
POST /api/v1/ingestion/receipts：外部模型或系统提交结果，但不获得自动采纳资格。

输出不得省略分页或 truncated。证据包存在数量预算，不是全历史数据库备份。outbox 是至少一次交付语义，消费者应按 event_id 或来源稳定键去重。
查询结果中的 validation_status 是结构语义校验状态；候选/采纳状态和证据可用性仍需要分别读取。
公开溯源系统只应消费已授权可展示的数据。内部原图、人员与设备信息不因入库自动公开；公开 GitHub 上传的是程序/文档/合成示例，活动数据库、真实资产和凭据继续排除。

现有 JSON-LD/Turtle 导出可投影受限关系网查询结果；本版没有承诺所有属性图特征与 RDF/OWL 的任意无损互转。要扩展交换规范应单独定义限定关系、时间、证据节点和稳定 URI 的映射契约。

十、管理员工作顺序

页面主导航：数据库总览、本体管理、数据接入、对象与关系、原件与断言。兼容扩展折叠为批次与溯源、设备采集。
本体管理提供创建本体、对象分类、关联对象、对象分组说明；单个本体可查看结构、编辑名称。
数据接入提供登记来源映射、接收结构化记录、填写观测、记录事件、上传原件、候选断言。
管理员先完成类/属性定义与对象分类，再登记来源映射；用样本预览检查原始字段到结果的对应，再正式接收。
遇到待映射或校验失败，查看回执的原文、错误和历次尝试，修正规则/分类后选择映射重试。不要删除原文，不自动选择看起来相似的属性。

十一、与梁子湖项目的接轨安排

第一步：取得一个来源的真实接口文档、脱敏样本、稳定对象/记录 ID、时间和单位说明。
第二步：用已有平台对象 ID 建立明确内部身份关联；需要时在适配器维护受控对照，不按名称模糊匹配。
第三步：管理员核对类属性边界，固定来源契约与映射版本，进行有效样本和错误样本预览。
第四步：使用来源稳定事件 ID 提交；核对原平台记录、标准化值、证据链、重放和失败重试。
第五步：代码层或溯源系统按 API 读取，展示结构校验/候选/证据状态，不把推测和实测混合。

真实厂家地址与凭据、来源到令牌的强绑定、PostgreSQL 实库、生产身份/TLS、容量/备份恢复尚需项目实际环境验收。
不新增完整身份平台或模型运行平台来完成这一阶段；外围能力通过明确接口和部署责任衔接。

十二、验收清单与交付边界

检查以下行为，而非仅确认页面能打开：
- 名称修改后旧对象和属性引用仍有效；并发名称更新被检测。
- 正确类属性可入库，错类/错单位/未知枚举不能静默通过。
- 有效时间外的分类不能解释历史观测；含义不明的数据保留待映射。
- 预览无持久写入；同来源重放不重复；内容改变冲突。
- 失败目标不留半条业务数据，原文与尝试保留；换新映射重试可追溯。
- 模型只产生带producer与输入证据的候选结果；系统不实际调用模型。
- 原图完整性、载体有效性、外部未处理分别显示；没有亮度或视觉诊断默认任务。
- 无认证/无角色/跨租户请求被拒绝，查询不返回其他租户数据。

测试结果以 implementation/验证结果.txt、tests/latest-results.xml 和本次交付状态文件为准。SQLite 行为测试、HTTP 边界测试、浏览器验证、PostgreSQL 与现场验收必须分开报告；未配置而跳过的检查不能记为通过。
这版交付是数据库核心工程改版，不等于生产部署完成，也不等于完整通用本体编辑器或农业专家系统。
